1. Clicking a text file should open it in the internal viewer
------------------------------------------------------------

Now:  clicking a panel row selects it; clicking the selected row (or
      double-clicking) dispatches Enter. Enter on a file is a dead end -- it
      just sets the message "<name> -- no action bound yet (F3 to view)".
      F3 works, but the obvious gesture does nothing useful.

Want: click-to-open on a file that the viewer can display.

Where: Invoke-McKey's 'enter' branch in src/Mc.PowerShell/App.ps1 -- the
       leaf case that currently only sets a message. Invoke-McViewCurrent in
       src/Mc.PowerShell/Viewer.ps1 already does the work, including deciding
       whether the entry is a real file on disk.

Decide first: mc's Enter on a file *executes* it. We deliberately do not
execute anything, and in read-only mode we must not. Options:
  a) Enter/click opens the viewer for anything viewable. Simple, safe,
     matches what the gesture implies. Diverges from mc.
  b) Enter opens the viewer for text and refuses to execute, with a message
     saying F3/F4 are the ways in.
  c) Enter executes in read-write mode only, views in read-only.
Leaning (a). Whichever, record it in docs/COMPAT.md, because mc's behaviour
is "execute" and the scorecard must not overstate parity again.

Also: Read-McViewerFile already detects binary content, so a click on a .exe
should say so rather than opening a screen of nothing.


2. Registry navigation does not open keys
-----------------------------------------

Symptom: in a registry panel, Enter (or click) on a subkey does nothing. The
         panel stays where it is and says nothing.

Diagnosed -- two separate faults:

  (a) The PSProvider source's Descend uses Convert-Path, which returns the
      provider-internal path, not a drive-qualified one:

          entry Key    : Microsoft.PowerShell.Core\Registry::HKEY_LOCAL_MACHINE\SOFTWARE\7-Zip
          Convert-Path : HKEY_LOCAL_MACHINE\SOFTWARE\7-Zip        <-- unusable

      Nothing can handle "HKEY_LOCAL_MACHINE\...": the FileSystem source's
      Test wants a drive letter, and Test-Path rejects it, so
      Get-McPanelSource throws. Convert-Path is right for the filesystem and
      wrong for every other provider.

      Fix: build the child path from the location we are already on --
      Join-Path $Location $Entry.Name -- and only use Convert-Path when the
      provider is FileSystem. Worth a helper next to Get-McParentPath, since
      the same asymmetry will bite Cert: and any module-supplied drive.

  (b) The failure is silent. Set-McPanelLocation returns $false and reverts
      to the previous location so the user is not stranded, but
      Invoke-McPanelEnter discards that with [void](...) and sets no message.
      A navigation that fails should say why.

Both are small. (b) is worth doing regardless of (a), because "nothing
happened and nothing was said" is how (a) stayed hidden.

Tests: tests/KeySequence.ps1 covers descending on the filesystem only. Add
       the provider case -- descend into HKLM:\SOFTWARE\<something> and assert
       the location actually changed -- which would have caught this.
